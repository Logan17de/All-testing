# Standalone provider authentication

Verified against provider primary documentation on 2026-10-05. Providers supply inference; the harness owns orchestration and tools. No Codex CLI, app-server, official-client impersonation, browser credential extraction, or denied-action fallback is needed for the documented OpenAI direct inference flow.

## OpenAI ChatGPT plan usage

OpenAI now documents [ChatGPT plan usage for open-source clients](https://developers.openai.com/siwc/token-sharing-open-source/sign-in). First registration uses the documented `dynamic_agent_client` entrypoint, the app's actual name and a stable per-host `ext_agent_host_id`. The user reviews permissions in the real browser. The callback returns the issued client ID used for code exchange and subsequent reauthorization. This flow does not need a client secret or partner API key. This differs from [identity-only website sign-in](https://developers.openai.com/siwc/website), which requires a registered website client and does not itself authorize model inference.

Implemented optional server-side plumbing: `apps/runtime/src/runtime-chatgpt-auth.ts`. Construction is inactive. `begin()` prepares fresh state, nonce and S256 PKCE; it must be called only after an explicit user action and an HTTP listener on `127.0.0.1:<port>/auth/callback` is ready. `complete()` consumes one callback, exchanges with the issued ID, verifies the ID token against OpenAI's published JWKS (RS256 only), checks issuer, audience, expiration, nonce and verified subject, then checks granted inference scopes. Returning sign-in cannot change account/client identity. Cancellation/clear prevents stale completion. Credentials remain private and memory-only; `account()` and JSON serialization expose no tokens. `accessToken()` is strictly a runtime credential accessor, never an RPC response. Near-expiry refreshes are serialized and rotate the token set together.

The optional `runtime-chatgpt-auth-http.ts` controller creates a numeric loopback callback listener only after explicit login action; it expires and closes the listener on completion or cancellation. Its HTTP handler supplies read-only status and explicit login/cancel/search actions behind the main runtime authentication checks. Account picker, persistent credential storage and remote sign-out remain incomplete. A browser on a different machine cannot reach a cloud runtime's loopback listener without a supported local companion or explicit port forwarding. Do not replace `127.0.0.1` with a public callback or `localhost`. Host identity must be stable and supplied by the runtime; this module does not create persistent identifiers or credentials. Persistence requires separate user confirmation and protected atomic storage; Windows needs suitable file ACLs rather than a claim that Unix mode bits suffice. `clear()` removes local credentials; it does not claim remote revocation. A finished sign-out workflow must implement discovery-based remote revocation and report unconfirmed revocation, as described in [accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions).

[Models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference) explicitly supports OAuth bearer credentials with the public `GET https://api.openai.com/v1/models` and `POST https://api.openai.com/v1/responses`. The model catalog uses `models`, account-specific `slug` and `display_name`, filtered by `visibility: "list"`; do not hardcode an account's available models. Each HTTP turn must set `store: false`, `stream: true` and supply full required history. A direct adapter must require `response.completed`, honor cancellation and refuse truncated/error streams. Model calls must never fall back to paid API credentials or another endpoint when a grant is denied.

The [preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) require instructions/developer messages rather than explicit system items, and prohibit HTTP `previous_response_id`, temperature, max-output limits, background/conversation and several other parameters. Function/custom tools must be namespaced (or supplied via additional-tools input items). Hosted MCP, native computer use, image generation, file search, Code Interpreter and Responses tool-search are unavailable on this route. The harness's own tools/MCP/agents are separate local capabilities; their implementation does not imply those proprietary services are available. The separate `runtime-codex-search.ts` bridge performs direct Responses inference with only the public `web_search` tool. It never launches Codex CLI or exposes filesystem, shell, function, computer, MCP or arbitrary tool execution. Configuration requires an explicit model and authenticated credential accessor; no denied provider call falls back to another provider or paid API credential. It requires completed inference with web-search output evidence and returns bounded text/citations. Account policy or model rejection of web search is reported as a provider error. Native coding-agent inference uses `runtime-chatgpt-model.ts`: text messages are sent as full history, system instructions become developer messages, and only explicitly offered functions are grouped under the `harness` namespace. Provider function calls are decoded after terminal completion for the harness to validate/approve/execute; the provider adapter executes nothing. The visible model catalog is read from the authenticated account, preserving server ordering. Vision and structured-output requests currently fail closed.

The preview route cannot accept a provider-side `max_output_tokens` cap. The native adapter omits that field and applies `maxOutputTokens` only as a local postresponse gate: reported output-token usage is required and must be within the requested budget before completed results or tool calls become available for execution. Byte limits, timeout, cancellation and native run/model-call budgets still apply. This does **not** prevent within-request spending overrun or hidden reasoning tokens. Exact provider-side per-request output/spending caps are unavailable in this flow. Opaque provider reasoning/encrypted reasoning history is not yet retained by the current provider-neutral message contract; lossless reasoning-model continuation/resume is incomplete and must not be claimed from text/function-history tests.

Validation: local loopback listener checks, a mocked search provider, and a mocked token endpoint and locally generated test signing key exercise authorization, valid and invalid claims, grant denial, one-time callbacks, cancellation, refresh serialization and secret-safe errors. They are not live-provider tests. No real registration, credentials, consent or model inference were performed.

## Claude and Grok

Keep subscription login separate from API-key integration. [Anthropic's authentication and credential policy](https://code.claude.com/docs/en/legal-and-compliance#authentication-and-credential-use) disallows third-party developers offering Claude.ai login in their own applications or routing Free/Pro/Max subscription credentials on users' behalf. It distinguishes an end user signing into the unmodified Claude Code binary from a third-party app collecting or using those tokens. Do not borrow Claude Code's client ID or token store; the standalone harness requires approved third-party terms/flow before adding subscription login. [The official Agent SDK plan-usage support article](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan) currently says the announced billing changes were paused and official Agent SDK/`claude -p`/third-party SDK apps continue to draw subscription limits. That establishes an official SDK/CLI path; it does not publish a general third-party OAuth client registration or authorize extracting tokens for this independent inference adapter. Using the official agent engine would require a separate architecture decision because this harness owns its own tool executor. The existing separately billed Anthropic API adapter remains gated by the user's decision.

[xAI API authentication](https://docs.x.ai/docs/api-reference) documents an API-key bearer credential. [Grok Build enterprise authentication](https://docs.x.ai/build/enterprise#authentication) documents official CLI OAuth2/OIDC through `auth.x.ai` and a CLI inference proxy, and [headless/ACP integration](https://docs.x.ai/build/cli/headless-scripting#acp) provides an official client bridge. Do not describe Grok OAuth as nonexistent. A general independently registered third-party subscription OAuth client and direct native inference contract were not established by those CLI docs; this harness must not borrow the official CLI client ID or extract its tokens. The existing separately billed xAI API adapter remains gated; do not silently substitute it for subscription login.
