# Harness msgs to the models

This inventories **this repository's own public, model-facing wording and related user/runtime notices**. It does not contain hidden assistant instructions, provider system prompts, private logs, credentials, or purported Codex internal prompts. Sources were inspected on 2026-10-05. Regenerate the source-derived appendix with `node scripts/refresh-model-message-inventory.mjs` after implementation changes. Source expressions in the appendix retain `${...}` placeholders rather than private example values. Public protocol compatibility does not establish proprietary prompt parity.

**Implemented** means the wording exists in code; it does not mean a capability is enabled, approved or live-provider verified. **Proposed** wording below is not sent by the current code. Paths are relative to `harness/`.

## Tool contracts and model-visible outcomes

Only offered, host-authorized tools are presented to a model. Built-in coding/action tools validate their supported arguments. MCP input validation now enforces a bounded supported assertion subset and rejects unsupported keywords; displaying a schema remains insufficient to claim universal JSON Schema enforcement for every external plugin. Each specification contains the tool name, description and JSON input schema. The source-derived appendix lists the repository-authored descriptions, schema field descriptions and exact input/output schema source expressions. Shared schema constants/helpers are references to code in the cited module; they are not fabricated JSON expansions. Names and schemas are code, not a promise that an operation can run on every platform.

Approval requests are sent to the user interface with the exact tool ID/arguments and expiry. The native model waits while the host awaits a decision. The existing 120-second native approval timer, rejection, cancellation and stale-workspace checks settle approval false; they do **not** inject a new model instruction. A denial is never a grant to retry through another executor/provider. Native mutation approvals are not claimed to be durable across a runtime restart.

## Instructions, selected skills and optional image transport

The instruction loader now accepts an explicit host-selected workspace-relative working directory and orders applicable AGENTS.md files from workspace root to that directory. Its exact wrapper is `Workspace instructions (${filePath}; applies to its directory and descendants):\n${body}`. The precedence notice is `Applicable AGENTS.md files are ordered from workspace root to selected working directory. Deeper directory instructions take precedence within that subtree; host and user instructions remain authoritative. Unrelated descendant instruction files are not loaded.` Catalog mode uses `Available workspace skill ${entry.name} (${filePath}; body not loaded): ${description}`; selected bodies retain the workspace-skill wrapper. These are model context only, never new execution grants. Limits and validation wording are in the source appendix.

Optional adapter image input is a wire shape `{role:"user",content:[{type:"input_image",image_url:"data:${mediaType};base64,${encodedBytes}",detail:"auto"}]}` derived from a trusted host artifact resolver. No image pixels or private artifact values are inventoried here. Production has no resolver, so this shape is not evidence of enabled native screenshot transmission. Default refusals use `MODEL_REQUEST_UNSUPPORTED` or the bounded input limit, not a new proprietary computer instruction.

## Installed plugin and graph scope wording

Installed granted tools can be offered by default; `runtime-agent-tool-policy.ts` intersects canonical IDs, recorded owner/version and node scope when offering and invoking. Unknown/ambiguous tool aliases do not grant execution authority. Child reads inherit the parent's effective fixed read scope; absent scope denies all. Durable per-chat `model` and `tools` lists are **tool restrictions for the model node and tool execution node**, not inference-model selection. Null preserves host-authorized defaults and [] denies all. Current UI says `By default all enabled, granted plugin tools are available. Restrictions apply to the next task; the current task keeps its existing scope. Mutation and external interaction consent still apply.` This is a user notice, not a model instruction or added grant.

`runtime-agent-plugin-tools.ts` snapshots bounded JSON arguments without invoking getters, checks active registered owner/version/exact adapter and grants around consent, and replaces implementation failures with a generic private-safe error. The source appendix below contains exact refusal wording and UI validation notices. None of these notices is automatically a new provider system prompt. Tool failure envelopes and delivery rules above govern model visibility.

## Desktop and browser consent

`runtime-desktop-session.ts` contains an optional local desktop controller and `runtime-windows-desktop.ts` an optional Windows driver. Explicit arming selects an inventoried monitor/window, bounds actions/time, and requires per-input consent plus separate screenshot-transmission consent. Tests use a mocked OS bridge and synthetic PNG; they do not establish real Windows execution. The UI says `No image is sent automatically by this page.` The ChatGPT adapter supports an optional trusted host image resolver, but production has none configured; native image attachment/transmission remains unavailable by default. Local preview/export does not establish a model-image integration.

The native browser session uses an ephemeral Playwright context, explicit task/domain consent and separate input approval. Browser model tool registration and guarded routes remain separately scoped; the manual host `npm run browser` CLI requires explicit arm/execute/approve or deny/stop actions. CLI consent alone does not establish autonomous model-browser execution. Domain/DNS routing is an application policy, not an OS network firewall. No existing browser profile or proprietary browser/computer prompts are imported.
Current desktop consent payload: `{task,generation,purpose:"input",action}` or `{task,generation,purpose:"transmission",artifactId}`. These are user consent requests, not new model instructions. The same distinction applies to MCP elicitation: server-provided titles/descriptions/schema are external content; supported UI decisions do not grant additional harness filesystem/process authority.
